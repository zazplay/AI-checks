# Invoice Processing System
### Презентація проєкту до технічної співбесіди

> Full-stack застосунок для завантаження, асинхронної обробки та аналізу інвойсів
> з AI-екстракцією даних і AI-асистентом, що **відповідає і виконує дії**.

**Live demo:** <https://invoice-prc.vercel.app> · логін `admin / admin`
**API + Swagger:** <https://invoice-prc-production.up.railway.app/docs>

**чіткі рішення, чисту архітектуру, асинхронний стан, що працює, і UI, який робить свою роботу.**

## Слайд 2. Технологічний стек

| Шар | Вибір | Чому |
|-----|-------|------|
| Backend | **NestJS + TypeScript** | Модульний DI ідеально лягає на декомпозицію черга / gateway / асистент |
| Frontend | **React + Vite + Mantine + React Query + Socket.IO** | Швидкий dev-цикл, готові компоненти, кеш-менеджмент із коробки |
| БД | **PostgreSQL (TypeORM, `jsonb`)** | `jsonb` для гнучкої схеми екстракції без міграцій під кожен формат |
| Черга / Jobs | **Redis + BullMQ** | Durable async-обробка, retries, rate limiting |
| Real-time | **Socket.IO** (події) + **SSE** (прогрес асистента) | Кожен транспорт під свою задачу |
| AI | **Claude (`claude-haiku-4-5`), Google Gemini, Groq** | Мульти-движок заради відмовостійкості й безкоштовних квот |
| Інфра | **Vercel + Railway (Postgres+Redis) + Cloudflare R2** | Реально задеплоєно й працює |

## Слайд 3. Архітектура (з висоти пташиного польоту)

```
            ┌─────────────┐     REST + WS + SSE     ┌──────────────────────┐
            │   Browser   │ ◀──────────────────────▶│   NestJS API (HTTP)  │
            │ React + RQ  │                          │  Auth · Invoices ·   │
            └─────────────┘                          │  Assistant · AI · WS │
                  ▲                                  └─────────┬────────────┘
                  │ invoice.created/updated/deleted            │ enqueue job
                  │ (Socket.IO broadcast)                      ▼
            ┌─────┴────────┐                          ┌──────────────────┐
            │ EventsGateway│ ◀── emit ── markStatus ──│  BullMQ Worker   │
            └──────────────┘                          │  (extraction)    │
                                                      └───┬──────────────┘
   ┌─────────────┐   ┌──────────┐   ┌──────────┐          │ vision/text
   │ PostgreSQL  │   │  Redis   │   │   R2/S3  │          ▼
   │ invoices    │   │ BullMQ   │   │  files   │   Claude · Gemini · Groq
   └─────────────┘   └──────────┘   └──────────┘
```

**Ключовий принцип:** БД — єдине джерело істини. Воркер пише статус у БД → gateway транслює подію → UI патчить кеш. Залежності модулів **ациклічні** (`Invoices → Processing`, без зворотного циклу).

## Слайд 4. Життєвий цикл інвойсу (асинхронний конвеєр)

```
POST /invoices ──▶ status=uploaded ──▶ emit invoice.created ──▶ enqueue BullMQ job
                                                                        │
   (запит повертається миттєво — файл уже в R2, рядок у БД)             ▼
                                              worker: markProcessing → emit updated
                                                                        │
                                              extraction cascade (per-attempt log)
                                                          │                  │
                                               успіх ◀────┘                  └────▶ помилка
                                                 │                                    │
                                        markCompleted                     recoverable → BullMQ retry
                                        + extractedData                   (3 спроби, backoff 5/10/20с)
                                        emit updated                               │
                                                                       terminal → UnrecoverableError
                                                                                   │
                                                                          markFailed → emit updated
```

- **Backpressure:** при черзі ≥ 5000 завдань upload отримує `429` ще до збереження файлу.
- **Rate limit:** не більше 8 завдань / 60с (захист безкоштовної квоти AI); надлишок **паркується, а не падає**.
- **Concurrency:** 2 інвойси паралельно (налаштовується через env).

## Слайд 5. AI-екстракція — каскад із fallback

Документ читають **vision-движки**, впорядковані за обраним primary-движком:

```
Claude vision ──▶ Gemini vision ──▶ Gemini alt ──▶ [PDF] Groq з text-layer
     │ score          │ score          │ score          │ score
     └────────────────┴────────────────┴────────────────┘
                       └─▶ best(attempts): +100 за «чистий» результат,
                            + впевненість·10, +vendor, +total, +line items
```

- **«Слабкий» результат** (пробуємо наступний движок): `outcome ≠ ok`, не інвойс, впевненість < 0.6, немає vendor+total, або **математика не сходиться** (`subtotal + tax ≠ total`).
- **Термінальна помилка** (падає одразу, без марних retry): не інвойс / впевненість < 0.4 / биті суми → `UnrecoverableError`.
- Антигалюцинаційні правила в промпті: **`null` замість здогадок**, впевненість відображає читабельність скана.
- Кожна спроба пишеться в `processingLog` і транслюється в UI **наживо** — видно, який движок читає документ. Переможець фіксується в `extractionSource`.

## Слайд 6. AI-асистент — «answer + act» (15 інструментів)

Ручний tool-use цикл (макс. **8 кроків**), однаковий набір інструментів конвертується під SDK Groq / Claude / Gemini (перемикається в рантаймі).

| Група | Інструменти |
|-------|-------------|
| **Читання/пошук** | `list_invoices`, `get_invoice`, `search_invoices`, `list_empty_invoices`, `query_invoices`, `filter_invoices`, `get_dataset`, `get_invoice_stats` |
| **Дії** | `retry_invoice`, `retry_all_failed`, `retry_failed_then_cleanup`, `reprocess_invoice`, `update_invoice` 🔒, `delete_invoice` 🔒, `delete_invoices` 🔒, `export_invoices` |
| **UI** | `render_chart`, `navigate_ui`, `suggest_actions` |

**Антигалюцинації (5 шарів):** UUID-guard на кожному id-інструменті · «find-then-act» у системному промпті · resolve-before-confirm (токен підписується лише для реальних id) · видалення невалідних UUID з тексту відповіді · model-readable помилки «спочатку знайди».

**🔒 Деструктивні дії** (видалення/редагування) гейтуються **HMAC-підписаним токеном** (TTL 5 хв): нічого не відбувається, доки користувач не натисне **Confirm**.

## Слайд 7. Real-time без polling

- **Socket.IO gateway** транслює `invoice.created` / `invoice.updated` / `invoice.deleted`.
- JWT перевіряється на **WebSocket handshake** — той самий токен, що й для REST.
- Frontend патчить кеш React Query **на місці** через `setQueryData` (`upsertInvoice`), без рефетчу основного списку.
- Похідні кеші (пагіновані сторінки, статистика) інвалідуються з **debounce 300 мс** — сплеск подій при batch-завантаженні стискається в один рефетч.
- На `reconnect` — одноразова інвалідація, щоб надолужити пропущені події (upsert ідемпотентний → конвергенція коректна).

**Чому два транспорти?** Socket.IO — постійний broadcast-канал станів (+ Redis-adapter для багатопроцесності); SSE — ефемерний прогрес однієї відповіді асистента («Thinking → Filtering → …») з кнопкою **Stop** (abort запиту).

## Слайд 8. Frontend UX — деталі, що вирізняють

- **Batch upload:** зона дропу сама перетворюється на сітку міні-карток по файлу (свій лоадер/статус), готові авто-сортуються вперед, один загальний прогрес-бар.
- Зона **заблокована**, доки йде завантаження **і доки черга бекенду ще розбирається** — новий батч не звалюється на необроблений.
- Клієнтська **конкурентність 4** одночасні аплоади (пул воркерів зі спільним курсором).
- **Деталь інвойсу:** прев'ю оригіналу (PDF/зображення), екстраговані дані, line items, таймлайн обробки, «Explain with AI», retry/reprocess.
- **Аналітика:** статуси, топ-вендори, витрати за валютами, тренд + AI-інсайти на запит.
- **Export:** Excel / CSV / ZIP оригіналів — кнопкою або через асистента.

## Слайд 9. Безпека та Auth

- Один користувач із env (`AUTH_USERNAME` / `AUTH_PASSWORD`), JWT при логіні.
- **Timing-safe** порівняння (SHA-256 + `crypto.timingSafeEqual`) — щоб час відповіді не зливав байти пароля.
- Глобальний `JwtAuthGuard` + декоратор `@Public()` для `/auth/login` та `/health`.
- Той самий JWT захищає REST і WebSocket.
- Порожній пароль **вимикає auth** (dev-зручність) — логиться попередженням на старті.
- Інструменти асистента — обгортки над `InvoicesService`, тож асистент дістає лише ті стани, що й REST API.

## Слайд 10. Що б покращив із більшим часом

З внутрішнього мульти-агентного код-рев'ю (`ai-artifacts/reviews/`):

- **Secret startup guard** — не стартувати з `dev-insecure-jwt-secret`, коли auth увімкнено; allowlist для CORS; rate-limit на логін/асистента.
- **Атомарний retry/reprocess** — `@VersionColumn` (оптимістичний лок), щоб закрити гонки дублів задач і lost-update.
- **Server-side abort при дисконекті** — щоб зупинена SSE-сесія не палила квоту AI на бекенді.
- **Content-sniff завантажень** — перевіряти magic bytes, а не лише MIME із запиту.
- **Міграції замість `synchronize`**, per-invoice WebSocket-кімнати, стрімінговий xlsx, **реальний автотест-набір** (зараз тести — ручні плани).

## Слайд 11. Як використовувався AI у розробці

- **Мульти-агентний Claude-воркфлоу** згенерував up-front design-pack (`ai-artifacts/context/`): паралельне дослідження по областях → адверсаріальний fact-check → синтез. Кожен документ зберігає секцію рев'ювера «Fact-check & corrections».
- Дизайн **еволюціонував під час білду**: від «лише Claude» до **мульти-движка (Claude/Gemini/Groq)** заради запасу безкоштовних квот.
- Друге **мульти-агентне рев'ю** (3 Sonnet + 2 Opus, крос-звірка + ручна перевірка) проаудитувало готовий код.
- Claude Code — упродовж усієї реалізації; артефакти лишені **as-is** згідно з вимогами завдання.

## Слайд 12. Демо-сценарій (живий показ)

1. Завантажую PDF → миттєво зʼявляється картка `uploaded` → наживо `processing` → `completed` із даними (**жодного refresh**).
2. Відкриваю деталь → прев'ю документа + екстраговані поля + таймлайн обробки (видно движок).
3. Завантажую «битий» файл → `failed` → тисну **Retry**.
4. Асистенту: *«покажи невдалі інвойси»* → картки; *«повтори всі невдалі»* → дія; *«експортуй completed у Excel»* → завантаження; *«видали інвойс X»* → **підтвердження** перед видаленням.
5. Перемикаю движок екстракції/чату в рантаймі — без редеплою.

## Слайд 13. Підсумок — що демонструє проєкт

- ✅ Усі вимоги TASK закриті, **плюс** export, аналітика, рантайм-перемикання движків, batch-upload з прогресом.
- **Архітектурна зрілість:** ациклічні залежності, БД як джерело істини, pluggable storage.
- **Async-стан, що працює:** BullMQ з retries/backoff, rate-limit, backpressure, термінальні vs відновлювані помилки.
- **Продумана AI-інтеграція:** каскад із fallback, scoring, антигалюцинації, гейт деструктивних дій підписаним токеном.
- **Усвідомлені компроміси:** свідомо зрізаний скоуп (один користувач) із задокументованим бэклогом — це готовий матеріал для питання «що б зробив інакше».

> Питання? Готовий заглибитись у будь-який модуль — від BullMQ-воркера до антигалюцинаційних гардів асистента.
